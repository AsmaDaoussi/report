\section{AI Services}

Three AI services enrich the platform with intelligent behaviour. Each was selected to match the available infrastructure and the nature of the data: a large language model for conversational assistance, a pre-trained transformer for sentiment classification, and a deterministic similarity algorithm for personalized recommendations.

% ── 5.2.1 AI CHATBOT ─────────────────────────────────────────────────────────
\subsection{AI Chatbot}

\subsubsection{Analysis}

\paragraph{Overview.}
The chatbot is a conversational assistant integrated into every page of the marketplace. It allows users to search the catalog, ask platform-related questions and retrieve order information in natural language. The system operates through a three-stage pipeline: intent classification, optional catalog data retrieval, and response generation. This architecture keeps latency low by routing simple requests locally and only invoking the language model when a free-form answer is required.

\paragraph{Stage 1 --- Intent Classification with TF-IDF and Linear SVM.}
Intent classification determines the purpose of a user message before any further processing. The platform uses a two-step approach: statistical vectorization followed by a linear classifier.

\vspace{4pt}
\begin{conceptbox}[aiBlue]{TF-IDF --- Term Frequency--Inverse Document Frequency}
\textbf{TF-IDF}~\cite{tfidf} is a statistical measure that quantifies the importance of each word in a message relative to the entire training corpus. Words that appear frequently in the message but rarely across all messages receive high scores, making them strong discriminators. Formally, for a word $w$ in document $d$ from corpus $D$:
\[
\text{TF-IDF}(w, d, D) \;=\; \frac{f_{w,d}}{\displaystyle\sum_{w' \in d} f_{w',d}} \;\times\; \log\!\left(\frac{|D|}{|\{d' \in D : w \in d'\}|}\right)
\]
Each message is transformed into a sparse numerical vector representing its lexical content.
\end{conceptbox}

\vspace{4pt}
\begin{conceptbox}[aiGreen]{Support Vector Machine}
A \textbf{Support Vector Machine}~\cite{svm} then classifies the TF-IDF vector. SVMs find the optimal separating hyperplane between training classes by maximizing the margin between the closest examples of each class (the \textit{support vectors}). The linear variant is particularly effective for text classification tasks, since TF-IDF feature spaces are generally linearly separable and the linear kernel trains efficiently on high-dimensional sparse data~\cite{sklearn}.
\end{conceptbox}

\paragraph{Stage 2 --- Retrieval-Augmented Generation.}
When a product-search intent is detected, the platform queries the asset catalog using keywords from the message and injects the matching results into the model's context window. This \textbf{retrieval-augmented generation} (RAG) pattern~\cite{rag} grounds the model's response in real catalog data and eliminates the risk of the model fabricating non-existent products.

\paragraph{Stage 3 --- Response Generation with a Large Language Model.}
The final response is generated by \textbf{Qwen2.5-72B-Instruct}~\cite{qwen25}, a large language model developed by the Qwen Team at Alibaba Cloud.

\vspace{4pt}
\begin{conceptbox}[aiPurple]{Transformer Architecture and Large Language Models}
Large language models are built on the \textbf{Transformer} architecture~\cite{transformer}, which relies on a \textit{self-attention mechanism} allowing every token in the input sequence to attend to every other token simultaneously, capturing long-range dependencies without recurrence. Pre-trained on massive text corpora and subsequently fine-tuned with instruction-following data, these models generate fluent, contextually coherent answers conditioned on a provided system prompt and conversation history.
\end{conceptbox}

The model is served through the Hugging Face Inference API~\cite{huggingface}, eliminating the need for local GPU infrastructure. A rule-based fallback is activated whenever the external service is unreachable, ensuring the assistant remains functional at all times.

% ── 5.2.2 REVIEW SENTIMENT ANALYSIS ──────────────────────────────────────────
\subsection{Review Sentiment Analysis}

\subsubsection{Analysis}

\paragraph{Overview.}
Every review submitted by a buyer is automatically analyzed to determine whether its content is positive, neutral or negative. This sentiment classification supports moderators in auditing large volumes of user feedback and provides sellers with an aggregated view of how their assets are perceived, without requiring manual reading of each entry.

\paragraph{Primary Model --- DistilBERT.}
The primary classification engine is \textbf{DistilBERT}~\cite{distilbert}, a compressed variant of the \textbf{BERT} architecture.

\vspace{4pt}
\begin{conceptbox}[aiBlue]{BERT --- Bidirectional Encoder Representations from Transformers}
\textbf{BERT}~\cite{bert} is a pre-trained deep bidirectional Transformer that reads the entire input sequence simultaneously, capturing context from both sides of each word. This bidirectional attention mechanism makes it significantly more effective at understanding negation and nuance than models that process text strictly left to right.
\end{conceptbox}

\vspace{4pt}
\begin{conceptbox}[aiGreen]{Knowledge Distillation and DistilBERT}
DistilBERT~\cite{distilbert} is obtained through \textbf{knowledge distillation}: a smaller \textit{student} model is trained to replicate the output distribution of a larger \textit{teacher} model (BERT), rather than learning from raw labels alone. The result retains approximately 97\,\% of BERT's performance on downstream tasks while using 40\,\% fewer parameters and running 60\,\% faster.
\end{conceptbox}

The variant used in this project was fine-tuned on the \textbf{Stanford Sentiment Treebank} (SST-2)~\cite{sst2}, a benchmark dataset of sentence-level sentiment annotations drawn from movie reviews. Its classification of short evaluative sentences transfers naturally to marketplace reviews. The model returns a binary label (positive or negative) alongside a confidence score; reviews with a confidence below 0.65 are mapped to the \textit{neutral} class to avoid committing to a label when the signal is ambiguous.

\paragraph{Fallback Model --- Logistic Regression.}
A secondary \textbf{Logistic Regression}~\cite{sklearn} classifier trained on TF-IDF features serves as an offline fallback when the cloud inference API is unavailable. Logistic Regression estimates the probability of class membership by applying the logistic function to a linear combination of input features. It produces a three-class output (positive, neutral, negative) and is well suited to this role because of its low computational footprint and interpretable decision boundaries. % ── 5.2.3 PERSONALIZED RECOMMENDATIONS ───────────────────────────────────────
\subsection{Personalized Recommendations}

\subsubsection{Analysis}

\paragraph{Overview.}
The recommendation system surfaces relevant assets to each user based on their interaction history. It follows a \textbf{content-based filtering} approach~\cite{cbf}, which derives user preferences from past behaviour and matches them against asset attributes rather than comparing users with one another. This design does not require a large user base to produce meaningful results, making it well-suited to a growing marketplace.

\paragraph{Similarity Measure --- Jaccard Index.}
Each asset is represented by its set of descriptive tags.

\vspace{4pt}
\begin{conceptbox}[aiOrange]{Jaccard Similarity Index}
The \textbf{Jaccard similarity index}~\cite{jaccard} quantifies the overlap between two sets $A$ and $B$ as the ratio of their intersection to their union:
\[
J(A,\,B) \;=\; \frac{|A \cap B|}{|A \cup B|}
\]
A value of 1 indicates perfectly identical sets; a value of 0 indicates no overlap at all. The Jaccard index is well suited to recommendation tasks based on tags because the attributes are binary (present or absent) and the sets vary widely in size across categories.
\end{conceptbox}

\paragraph{User Profile Construction.}
The user's preference profile is built from four interaction types, each weighted according to the strength of preference it expresses:

\paragraph{Diversity and Cold-Start Handling.}
To prevent the ranked list from being dominated by near-identical assets, a post-processing diversity pass demotes any item whose tag overlap with a higher-ranked result exceeds 70\,\%. Users with no recorded interactions — guests and newly registered accounts — receive a trending list ranked by recent download and purchase frequency, and the interface displays ``Trending Now'' rather than ``Recommended for You'' in this cold-start state.

The recommendation page is accessible to both authenticated and anonymous users. Users with sufficient interaction history receive a personalized ranking; all others see the trending catalog. The interface is visually consistent with the standard catalog pages.

\section{Security Hardening}

Three independent security mechanisms protect the platform against the most common attack vectors catalogued in the OWASP Top Ten~\cite{owasp}.

\begin{itemize}[leftmargin=2em, itemsep=6pt]
  \item \textbf{Rate limiting.}
        Each sensitive endpoint is protected by a per-IP request ceiling. Authentication
        attempts are limited to ten requests per fifteen-minute window, and account
        registration is capped at five per hour. This mitigates brute-force and
        credential-stuffing attacks by making exhaustive enumeration computationally
        impractical.

  \item \textbf{Token revocation.}
        Authentication tokens are immediately invalidated upon logout through a
        server-side blacklist consulted on every authenticated request. This ensures
        that a token intercepted after the user has signed out cannot be reused,
        regardless of its expiry date.

  \item \textbf{Magic-byte file validation.}
        Uploaded images are validated at the binary level against the known
        \textbf{magic bytes} of accepted formats (PNG, JPEG, WebP, GIF). Magic bytes
        are fixed byte sequences at the start of a file that identify its true format
        independently of the filename or MIME type declared by the client. A file
        whose binary header does not match its declared type is rejected before
        reaching storage, preventing MIME-confusion attacks in which a malicious file
        is disguised as a safe image.
\end{itemize}

Beyond these three mechanisms, the OWASP coverage includes: broken access control addressed through the RBAC permission model, injection risks eliminated through parameterized database queries throughout the data layer, and security misconfiguration mitigated by a strict CORS policy, security-oriented HTTP headers and mandatory environment-variable validation at application startup.

\section{VR/AR Immersive Preview}

\subsection{Analysis}

\paragraph{Browser-Native Immersive Web.}
The immersive preview feature is delivered entirely through the browser, with no plugin or companion application required on the user's side. This is made possible by a recent W3C standard that exposes virtual and augmented reality hardware directly to web pages.

\vspace{4pt}
\begin{conceptbox}[aiPurple]{WebXR Device API}
The \textbf{WebXR Device API}~\cite{webxr} is a W3C standard that provides browsers with a unified interface for accessing virtual and augmented reality hardware. It abstracts the differences between headset models, controller layouts and spatial tracking systems, allowing a single web application to deliver immersive experiences across a variety of XR devices without platform-specific adaptations.
\end{conceptbox}

Because the API is implemented natively in modern browsers, the immersive preview is
accessible to anyone owning a compatible headset, without any installation step.

\paragraph{3D Rendering and Stereo Mode.}
The asset viewer is powered by \textbf{Three.js}~\cite{threejs}, a JavaScript library
that abstracts the low-level WebGL rendering pipeline. When a user enters immersive
mode, the renderer transitions to \textbf{stereoscopic projection}, producing a
separate image frame for each eye at the correct inter-pupillary offset to create a
convincing perception of depth. In augmented reality mode, the rendered 3D asset is
composited over the live camera feed provided by the headset's passthrough cameras,
allowing the user to inspect the object within their physical environment.

To maintain rendering correctness in XR sessions, visual post-processing effects
that rely on multi-pass framebuffer operations are deactivated during immersive
rendering. These effects are not designed for the stereo framebuffer required by
headsets and would otherwise cause visual artefacts or rendering errors.

\paragraph{Hardware Validation.}
The feature was validated on a \textbf{Meta Quest 3}~\cite{metaquest} mixed-reality
headset. The device was connected to the same local network as the development server
and accessed the application through its built-in browser over HTTPS, which is
required by the WebXR specification. Two modes were tested: a fully immersive
\textbf{VR mode} in which the user is surrounded by the rendered 3D scene, and a
\textbf{passthrough AR mode} in which the asset is overlaid on the real environment
captured by the device's colour cameras. Both modes operated correctly, confirming
that the platform delivers an authentic WebXR experience on consumer mixed-reality
hardware.

\subsection{Realization}

On any compatible 3D asset detail page, the user can enter VR or AR mode directly from
the browser with a single click. In VR mode, the asset is rendered at true real-world
scale inside the headset, allowing buyers to evaluate proportions and surface detail
before purchasing. In AR mode, the asset is placed within the user's physical
environment, which is particularly useful for architectural models and large-scale
environment packs.

\section{Deployment on Hostinger VPS}

The platform is deployed for production on a \textbf{Hostinger VPS}. The deployment
configuration covers the reverse proxy, the process supervisor and an automated
continuous-delivery workflow that handles every release from source to live server.

\subsection{Target Infrastructure}

Three independent tiers handle different concerns:

\begin{itemize}
  \item \textbf{Hostinger VPS}: hosts the Node.js backend (Express API) and serves the
        two built React applications (Marketplace and Workspace) as static files.
  \item \textbf{Supabase} (cloud-hosted): handles the PostgreSQL database and the asset
        file buckets. No database instance is needed on the VPS.
  \item \textbf{Hugging Face Inference API}: serves the LLM and DistilBERT models remotely;
        no GPU hardware is required on the server.
\end{itemize}

\subsection{Key Deployment Concepts}

\begin{itemize}
  \item \textbf{Virtual Private Server (VPS):} an isolated virtual machine running
        Ubuntu~22.04 LTS, providing full root access without the cost of dedicated hardware.
  \item \textbf{Nginx (reverse proxy):} terminates HTTPS, serves the static React builds
        from \texttt{/var/www/}, and forwards \texttt{/api/*} and \texttt{/socket.io}
        traffic to the Express backend on port~3001.
  \item \textbf{PM2 (process manager):} keeps the Node.js process alive, restarts it on
        crash, enables zero-downtime reloads on new deploys, and manages log rotation.
  \item \textbf{Let's Encrypt + Certbot:} free SSL certificates renewed automatically
        every 90 days; HTTPS is mandatory for WebXR features to work in the browser.
  \item \textbf{Environment variables (\texttt{.env}):} keep secrets (JWT secret, database
        credentials, Stripe keys, Hugging Face token) out of the source code and out of the
        Git history entirely.
\end{itemize}

\subsection{CI/CD Pipeline}

A GitHub Actions workflow (\texttt{.github/workflows/cd.yml}) automates the release on
every push to \texttt{main}:

\begin{enumerate}
  \item Install dependencies and run lint and integration tests.
  \item Build both React frontends with \texttt{npm run build}.
  \item SSH into the Hostinger VPS, pull the latest code, copy the built
        \texttt{dist/} folders to \texttt{/var/www/}, and call \texttt{pm2 reload
        igs-backend} for a zero-downtime restart.
\end{enumerate}

Deployment secrets (\texttt{VPS\_HOST}, \texttt{VPS\_USER}, \texttt{VPS\_SSH\_KEY}) are
stored in GitHub repository secrets and never appear in workflow logs.
