\chapter{CI/CD \& Deployment}

\section*{Introduction}
This chapter describes the Continuous Integration and Continuous Delivery pipeline implemented for IGS Marketplace, the Docker-based containerization strategy, and the production deployment architecture.

% ---- 8.1 CI/CD PIPELINE ----
\section{CI/CD Pipeline}

The pipeline is implemented with \textbf{GitHub Actions}, triggered on every push or pull request targeting \texttt{main}. It runs three sequential jobs:

\begin{enumerate}
  \item \textbf{lint-build} — static analysis and compilation check for frontend and backend.
  \item \textbf{test} — automated test suite execution (needs: lint-build).
  \item \textbf{docker-publish \& deploy} — builds Docker images, pushes to DockerHub, and updates the production server via SSH (only on \texttt{main} branch pushes).
\end{enumerate}

The GitHub Actions runner authenticates to the production server using an RSA key pair (4096-bit) stored as a GitHub Actions Secret. After Docker images are pushed to DockerHub, the runner connects via SSH and instructs \texttt{docker-compose} to pull the latest images and restart the containers with zero manual intervention.

% ---- 8.2 CONTAINERIZATION ----
\section{Containerization with Docker}

Docker packages each service into a reproducible image, guaranteeing identical behavior across development, CI, and production environments.

\begin{itemize}
  \item \textbf{Backend (Express.js):} A Node 20 Alpine image installs production dependencies only, copies the source, and starts the server on port 3001.
  \item \textbf{Frontend (React/Vite):} A multi-stage build — the first stage compiles the Vite bundle inside a Node container; the second stage copies the \texttt{dist/} output into a lightweight Nginx image for static serving.
  \item \textbf{Database:} The official PostgreSQL 16 Alpine image with a persistent named volume for data durability.
\end{itemize}

A single \texttt{docker-compose.yml} orchestrates all three services (\texttt{db}, \texttt{backend}, \texttt{frontend}) on an isolated Docker network, with \texttt{depends\_on} ensuring startup order. Environment variables are injected from a server-side \texttt{.env} file at runtime — no credentials are committed to the repository.

% ---- 8.3 NGINX REVERSE PROXY ----
\section{Nginx Reverse Proxy}

Nginx serves as both the static file server for the React bundle and a reverse proxy routing \texttt{/api/*} requests to the Express backend container. This single entry point simplifies TLS termination and eliminates browser CORS issues. The \texttt{try\_files} directive ensures React Router's client-side routes are handled by the SPA rather than returning a 404 from Nginx.

% ---- 8.4 DEPLOYMENT STRATEGY ----
\section{Deployment Strategy}

\subsection{Image Publication and Remote Update}

On every successful pipeline run on \texttt{main}, the workflow authenticates to DockerHub using stored secrets and pushes fresh \texttt{igs-backend} and \texttt{igs-frontend} images tagged \texttt{latest}. The deploy job then SSHs into the production server and runs \texttt{docker-compose pull \&\& docker-compose up -d --remove-orphans}, delivering zero-downtime rolling updates.

\subsection{Database Migrations}

Schema migrations are applied sequentially using numbered SQL files (\texttt{001\_*.sql} through \texttt{018\_*.sql}). When a deployment introduces schema changes, the migration is executed inside the \texttt{db} container before the backend restarts, keeping schema and application code in sync.

\section*{Conclusion}
The GitHub Actions CI/CD pipeline provides end-to-end automation from commit to production. Docker containerization ensures environment consistency, Nginx consolidates the frontend and API behind a single entry point, and GitHub Secrets ensure no credential ever reaches the repository. This infrastructure gives the platform a production-grade, reproducible, and maintainable deployment foundation.
