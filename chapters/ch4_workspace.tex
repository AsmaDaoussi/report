\chapterintro{%
This chapter presents Sprint~3 and Sprint~4. Sprint~3 closes the production loop on the
public marketplace: sellers request access and upload assets, administrators moderate the
queue with full approve/reject/edit workflows, buyers leave ratings and written reviews,
peer-to-peer trades become possible, and the Creator Studio dashboard gives each seller a
full view of their revenue and downloads. Sprint~4 then delivers the internal
\textbf{IGS Workspace}: project boards, task tracking, a real-time team chat, a calendar,
intern asset-request management, voucher issuance and the full administrative control
panel covering users, roles, orders, categories and audit logs. AI-driven features (review
sentiment analysis, recommendations and the chatbot) are deliberately deferred to Sprint~5
where they are presented as a coherent block alongside security hardening and deployment.%
}

\subsection{Sprint 3 Realization}

\paragraph{Upload flow.}
Files are uploaded in two stages: \texttt{POST /api/upload/image} uploads the thumbnail to
\texttt{assets-images} with magic-byte validation (PNG, JPG, WEBP, GIF), then
\texttt{POST /api/upload/asset} uploads the asset file to \texttt{assets-files} with
category-specific MIME-type filtering. Once both uploads return storage paths, the frontend
calls \texttt{POST /api/assets} with the metadata; the asset is created with status
\texttt{pending} and enters the moderation queue.

When an internal user (employee, intern, admin) uploads an asset, the backend forces
\texttt{seller\_id = '49475300-0000-4000-8000-000000000001'} (the IGS Studio UUID) and sets
\texttt{uploaded\_by\_user\_id = req.user.id} for attribution.

\paragraph{Moderation queue.}
Administrators access \texttt{/moderation} where two tabs surface pending submissions:
external sellers (status \texttt{pending}) and intern uploads (status
\texttt{pending\_supervisor}). Each row is expandable to show the asset metadata; the
admin can attach a review note and click \emph{Approve} or \emph{Reject}. Decisions trigger
notifications to the seller.

\paragraph{Reviews and ratings.}
Users who own an asset can leave one review composed of a star rating
(\texttt{asset\_ratings}) and a written body (\texttt{asset\_reviews}). The endpoint
\texttt{POST /api/assets/:id/reviews} verifies ownership before accepting a submission.
Reviews are displayed in chronological order on the asset detail page. The
\texttt{ai\_sentiment} column on the review record is reserved for the automated
sentiment-analysis pipeline introduced in Sprint~5.

\paragraph{Notifications.}
Each significant action (review left, request accepted, asset moderated, trade proposed)
triggers a row in the \texttt{notifications} table. The frontend polls
\texttt{GET /api/notifications} on app mount and refreshes through the Socket.IO
\texttt{notif:new} event. A \texttt{platform} column (\texttt{marketplace}, \texttt{workspace}
or \texttt{both}) controls which interface receives the entry.

\paragraph{Creator studio.}
The creator studio (\texttt{Pages/Studio.jsx}, permission \texttt{view\_own\_stats})
exposes six stat cards (total revenue, total sales, pending assets, active listings, total
downloads, total views), a recent-sales list and a paginated asset table with status
badges, counts, revenue and an \emph{Edit} link per row. Data comes from
\texttt{GET /api/seller/dashboard} and \texttt{GET /api/seller/assets}.

\paragraph{Trades.}
\texttt{Pages/Trade.jsx} lets a user offer one of their owned assets in exchange for an
asset owned by another user. Each trade has a state machine (\texttt{pending /
accepted / rejected}) and triggers notifications to both parties.

\subsection{Sprint 3 Conclusion}
Sprint~3 closes the production loop on the public marketplace. Sellers can request access,
publish assets and follow their performance through the creator studio dashboard.
Administrators control the catalog through the moderation queue. Buyers can rate, review
and propose peer-to-peer trades, while notifications keep every actor informed of state
changes. The AI-driven sentiment classification and the recommendation engine that build
on these reviews are introduced in Sprint~5.

\subsection{Sprint 4 Realization}

\paragraph{Application structure.}
The workspace is a standalone Vite/React application at
\texttt{MarketPlace/IGS\_Workspace/}, proxying \texttt{/api} and \texttt{/socket.io} to
the backend on port 3001. The provider stack is
\texttt{ThemeProvider $\to$ AuthProvider $\to$ ChatProvider}. The same
\texttt{localStorage['igs\_token']} written by the marketplace login is reused, so
internal users switch between the two apps without re-authenticating.

\paragraph{Role-gated navigation.}
The sidebar is divided into four collapsible sections, each gated by minimum role:

\begin{table}[H]
\centering
\caption{Workspace sidebar sections and access requirements}
\begin{tabular}{|L{2.8cm}|C{2.5cm}|L{7.5cm}|}
\hline
\textbf{Section} & \textbf{Min Role} & \textbf{Pages} \\

\hline

\hline
Management & admin        & Assets, Orders, Users, Moderation, Role Requests, Categories, Vouchers \\

The \texttt{<RequireRole>} component wraps protected routes; on access denial it redirects
to \texttt{/} with \texttt{\{ accessDenied: true, required: min \}} in location state, so
the Dashboard shows an inline banner rather than a silent empty page.

\paragraph{Task board, projects and calendar.}
The task page implements a Kanban board backed by \texttt{workspace\_tasks}; tasks move
between \texttt{todo}, \texttt{in\_progress}, \texttt{review} and \texttt{done} columns
and carry priority badges (\texttt{low / medium / high / urgent}). The projects page
groups tasks under a parent project with owner, status and date range. The calendar
renders task due dates and project milestones in a monthly grid.

\paragraph{Real-time chat.}
The chat page connects to a Socket.IO~\cite{socketio} layer; conversations are grouped by
channel (project-based) or direct messages. The JWT is passed as \texttt{auth.token} at
connection time and validated on every socket event.

\paragraph{Moderation and administration.}
The moderation page presents two tabs: \emph{Pending Assets} (external submissions) and
\emph{Intern Uploads} (\texttt{pending\_supervisor}). The user, order, category and
voucher pages provide full CRUD interfaces. The role-requests page lists role-upgrade
applications with a filter (pending / approved / rejected) and an inline approve/reject
control that sends a notification to the applicant.

\paragraph{System pages.}
The roles-and-permissions page fetches \texttt{GET /admin/roles-with-permissions} (each
role with its full permission name array and a live user count). The audit-log page
exposes a filterable, paginated view of the \texttt{audit\_logs} table with color-coded
action badges and expandable JSON details. The settings page wires the commission rate
section to \texttt{GET/PUT /api/admin/config/commission}.

\paragraph{Intern workflow.}
The intern asset request workflow is:
\begin{enumerate}
  \item The intern opens an IGS-owned paid asset and clicks \emph{Request Access}.
  \item A modal collects a justification note (\texttt{intern\_asset\_requests.message}).
  \item The assigned supervisor receives a notification and reviews the request from the
        workspace moderation page.
  \item On approval, the asset is added to \texttt{user\_downloads} and the intern is
        notified.
  \item Rejected requests include a \texttt{review\_note}.
\end{enumerate}
Intern accounts also expire automatically: the \texttt{authenticate} middleware suspends
expired interns on the next API call.

\subsection{Sprint 4 Conclusion}
At the end of Sprint~4 the studio team has a fully functional internal ERP. Daily

\section*{Conclusion}
This chapter delivered the marketplace's content production loop (Sprint~3) and the
internal operations dashboard (Sprint~4). The platform is now feature-complete for both
the public marketplace and the studio team. The next chapter covers Sprint~5: the AI
chatbot, the security hardening layer and the proposed deployment pipeline.
