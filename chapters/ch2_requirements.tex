% ---- 2.2 NEEDS IDENTIFICATION ----
\section{Needs Identification}

The functional requirements describe what each category of actor is expected to accomplish through the platform.

\subsection{Functional Requirements}



\textbf{Visitor:}

\begin{itemize}[label=---,leftmargin=2em]
  \item \textbf{Register an Account:} create an account using email/password or through an OAuth provider (Google, GitHub). 
  \item \textbf{Browse the Catalog:} browse the public catalog by type(models, textures, shaders ...), search by name, and filter.
  \item \textbf{Preview an Asset:} inspect asset details and preview them in the browser or in VR/AR.
  \item \textbf{Use the AI Chatbot:} chat with a bot.
  \item \textbf{Get Recommendations:} consult trending asset suggestions.
\end{itemize}

\textbf{Member :}

\begin{itemize}[label=---,leftmargin=2em]
  \item \textbf{Authenticate:} sign in, sign out and recover the account through a password-reset email.
  \item \textbf{Manage Profile:} view and update personal information (display name, bio, avatar, password).
  \item \textbf{View Notifications:} consult the notification feed for orders, requests and moderation events.
  \item \textbf{Manage Cart:} add and remove assets from the personal cart.
  \item \textbf{Checkout and Pay:} pay through Stripe.
  \item \textbf{Manage Library:} access and download free or purchased assets.
  \item \textbf{Manage Reviews:} rate, write, edit and like reviews on owned assets.
  \item \textbf{Request Seller Access:} submit a justified request to be promoted to the seller role.
  \item \textbf{Use the AI Chatbot:} ask marketplace questions in natural language with personalized context.
  \item \textbf{Get Recommendations:} consult personalized asset suggestions based on purchase and download history.
\end{itemize}

\textbf{Seller:}

\begin{itemize}[label=---,leftmargin=2em]
  \item \textbf{Upload an Asset:} publish assets with files, thumbnails, metadata and pricing.
  \item \textbf{Request Asset Edit:} request modifications on already-approved assets without bypassing moderation.
  \item \textbf{Access Creator Studio:} consult personal sales statistics and per-asset performance.
  \item \textbf{Open Support Tickets:} communicate with the moderation team through a ticketing system.
  \item \textbf{Manage Trades:} propose, accept, reject or cancel asset exchanges.
\end{itemize}

\textbf{Intern (Workspace + Marketplace):}

\begin{itemize}[label=---,leftmargin=2em]
  \item \textbf{Request Asset Access:} request access to paid marketplace assets with a written justification.
  \item \textbf{Redeem Vouchers:} redeem discount codes issued by authorized staff.
  \item \textbf{Manage Tasks:} create, assign, update and track tasks on a Kanban board.
  \item \textbf{Participate in Projects:} consult assigned projects.
  \item \textbf{Use Team Chat:} communicate in real time via channels and direct messages.
  \item \textbf{Use the Calendar:} consult task deadlines, project milestones and personal events.
  \item \textbf{Manage Calendar Events:} create, edit and delete personal events on the calendar.
\end{itemize}

\textbf{Employee:}

\begin{itemize}[label=---,leftmargin=2em]
  \item \textbf{Approve Intern Asset Requests:} approve or reject intern asset access requests with a note.
  \item \textbf{View Reports:} consult platform analytics on revenue, sales and per-category performance.
  \item \textbf{Track Performance:} consult personal and team performance metrics.
  \item \textbf{Create Projects:} create projects, assign members and monitor progress.
\end{itemize}

\textbf{Administrator:}

\begin{itemize}[label=---,leftmargin=2em]
  \item \textbf{Manage Users:} create internal users, assign or revoke roles and update account status.
  \item \textbf{Manage Role Requests:} approve or reject member-to-seller upgrade requests.
  \item \textbf{Moderate Assets:} approve, reject or hide submitted catalog assets and intern uploads.
  \item \textbf{Manage Categories:} create, edit and deactivate asset categories.
  \item \textbf{Manage Vouchers:} issue, edit and revoke voucher codes.
  \item \textbf{Manage Orders:} consult orders and update their status.
  \item \textbf{Manage Teams:} create teams, add or remove members and assign team roles.
  \item \textbf{Handle Support Tickets:} consult seller tickets, reply and update ticket status.
\end{itemize}

\textbf{Super Administrator:}

\begin{itemize}[label=---,leftmargin=2em]
  \item \textbf{Consult Audit Logs:} consult the full audit trail of all platform actions with filtering.
  \item \textbf{Configure Roles \& Permissions:} consult and edit the permission set attached to each role.
  \item \textbf{Configure Platform Settings:} control global configuration including the commission rate.
\end{itemize}

Alongside these functional capabilities, the system must also satisfy a set of quality and reliability constraints.

% ---- 2.3 NON-FUNCTIONAL REQUIREMENTS ----
\subsection{Non-Functional Requirements}

\textbf{Security :} the application must guarantee the confidentiality and integrity of user data. Access must be controlled based on roles and permissions, and all sensitive actions must be traceable.

\textbf{Performance :} the application must maintain a minimal response time and remain responsive even with large volumes of content and simultaneous users.

\textbf{Reliability :} the application must always be able to function correctly. Errors must be handled gracefully without disrupting the user experience.

\textbf{Scalability :} the system must be designed to support growth in users, assets and traffic without requiring major structural changes.

\textbf{Usability :} the system must be simple and intuitive to use. Navigation between pages must be smooth, and the interface must be accessible across different devices.

\textbf{Maintainability :} the architecture must make it easy to add new features, fix issues and apply updates without impacting the rest of the system.

These requirements were organized into a prioritized backlog and distributed across five development sprints.

% ---- 2.5 ARCHITECTURE ----
\section{Project Architecture: 3-Tier}

The project follows a \textbf{three-tier architecture}: \\
Three-Tier Architecture, also known as three-layer architecture, organizes applications 
into three logical and physical layers: the presentation layer, the business logic layer, 
and the data access layer. This separation allows each layer to be developed, maintained,
and scaled independently, improving flexibility and reducing the risk of system-wide issues
when changes are made.
\begin{itemize}
  \item \textbf{Presentation Layer (UI Layer):} Handles the user interface and interaction, displaying data and capturing user input.
  \item \textbf{Business Logic Layer (Application Layer):} The core of the application where rules, workflows, and data processing occur.
  \item \textbf{Data Access Layer (Persistence Layer):} Manages storage, retrieval, and management of data, abstracting databases and external APIs from upper layers.
\end{itemize}
\begin{figure}[H]
\centering
\includegraphics[width=0.75\textwidth]{images/description/3-tier-architecture.png}
\caption{Three-Tier Architecture}
\label{fig:3-tier-architecture}
\end{figure}

\subsection{Backend Layered Architecture}

The backend maps the business-logic tier onto four internal layers:

\begin{itemize}[leftmargin=2em,itemsep=3pt]
  \item \textbf{Routes layer} (\texttt{routes/}) --- declares HTTP endpoints, chains middleware (JWT authentication, role/permission checks, rate limiters, input validators) and delegates execution to a controller.
  \item \textbf{Controllers layer} (\texttt{controllers/}) --- handles the HTTP request and response objects, orchestrates calls to repositories and services, and formats the JSON reply.
  \item \textbf{Repositories layer} (\texttt{repositories/}) --- contains all raw parameterised SQL executed through the PostgreSQL connection pool; no SQL appears outside this layer.
  \item \textbf{Services layer} (\texttt{services/}) --- encapsulates cross-cutting concerns: file storage (Supabase), audit logging, token revocation, AI inference calls and recommendation scoring.
\end{itemize}

This strict separation means that swapping the database engine, replacing a cloud service or adding a new route never requires changes to more than one layer.

\subsection{Frontend Architecture}

Both the Marketplace and the Workspace are built as independent React single-page applications using \textbf{HashRouter} (paths prefixed with \texttt{\#/}), so the web server never needs to handle deep-link URLs — only the root path is served.

Application-wide state is managed through a chain of React Context providers mounted at the root of each app:

\begin{enumerate}[leftmargin=2em,itemsep=3pt]
  \item \texttt{AuthContext} --- stores the JWT and the decoded user profile; handles OAuth callback parsing and logout.
  \item \texttt{PermissionsContext} --- exposes helper functions \texttt{can(permission)}, \texttt{hasRole(role)} and \texttt{hasMinLevel(n)} used by every protected route and conditional UI element.
  \item \texttt{CartContext} --- mirrors the server-side cart and synchronises additions and removals in real time.
  \item \texttt{NotificationContext} --- subscribes to Socket.IO events and maintains the unread notification counter across pages.
\end{enumerate}

All HTTP calls are routed through a shared \textbf{Axios instance} (\texttt{services/api.js}) that automatically attaches the \texttt{Authorization: Bearer} header from local storage, so individual pages never handle authentication headers manually.
