% ---- 2.1 ACTORS ----
\section{Actors Identification}

The platform is used by external marketplace users and by internal IGS collaborators. Access
rights are controlled through a role-based access control model (RBAC), where each role
receives a set of permissions adapted to its responsibilities.

\begin{itemize}[label=---,leftmargin=1.8em,itemsep=2pt]
  \item \textbf{Visitor}
  \item \textbf{Member}
  \item \textbf{Intern}
  \item \textbf{Employee}
  \item \textbf{Administrator}
  \item \textbf{Super Administrator}
\end{itemize}

\section{Needs Identification}



\subsection{Functional Requirements}

The functional requirements are organized into three categories: shared requirements that apply to all users, external requirements for external users, and internal requirements for internal users, here the hierarchy is applied.

\textbf{Any user can }
\begin{itemize}
  \item Login via authentication providers (email, google, github).
  \item Manage profile : a user can view and update their profile information, including name, email, password and profile picture.
  \item Browse the public catalog of assets with different categories (models, textures, animations, shades, 2d, environments).
  \item Search assets by name.
  \item Filter assets by different criteria (categories, price, tags, discount).
  \item Consult asset details and reviews.
  \item Preview assets on website or in VR.

\end{itemize}

\textbf{Member can}
\begin{itemize}
  \item Create an account via email, google or github.
  \item Add assets to the cart, remove them, and proceed to checkout.
  \item Rate, review and like assets.
  \item View personal library.
  \item download free or purchased assets.
  \item Trade with others.
  \item Request seller access.
  \item Receive notifications
\end{itemize}

\textbf{Seller}
\begin{itemize}
  \item Create an account via email, google or github.
  \item Upload assets.
  \item Communicate with the moderation team via ticketing system.
  \item Request edits on already approved assets.
  \item Consult personal asset statistics and seller analytics.
\end{itemize}

\textbf{Intern }
\begin{itemize}
  \item Upload internal assets.
  \item Request access to paid marketplace assets with a justification.
  \item Redeem vouchers generated by authorized reviewers.
  \item Collaborate through internal projects, tasks, documents, dashboards, and real-time chat.
\end{itemize}
\textbf{Employee }
\begin{itemize}
  \item Upload internal assets.
  \item Manage intern requests by approving or rejecting them based on the provided justification.
  \item Collaborate through internal projects, tasks, documents, dashboards, and real-time chat.
\end{itemize}

\textbf{Administrator }
\begin{itemize}
  \item Upload internal assets.
  \item Manage users, roles, permissions and role requests.
  \item Moderate submitted assets, edit requests, intern uploads, and intern asset requests.
  \item Manage vouchers, categories, commission configuration, and platform settings.
  \item Consult platform analytics, audit logs, orders and notifications.
\end{itemize}
\textbf{Super Administrator }
\begin{itemize}
  \item Upload internal assets.
  \item view audit logs.
  \item Manage platform settings.
  \item manage users roles.
\end{itemize}

% ---- 2.5 ARCHITECTURE ----
\section{Project Architecture: 3-Tier}

The project follows a \textbf{three-tier architecture}: \\
Three-Tier Architecture, also known as three-layer architecture, organizes applications 
into three logical and physical layers: the presentation layer, the business logic layer, 
and the data access layer. This separation allows each layer to be developed, maintained,
and scaled independently, improving flexibility and reducing the risk of system-wide issues
when changes are made.
\begin{itemize}
  \item \textbf{Presentation Layer (UI Layer):} Handles the user interface and interaction, displaying data and capturing user input.
  \item \textbf{Business Logic Layer (Application Layer):} The core of the application where rules, workflows, and data processing occur.
  \item \textbf{Data Access Layer (Persistence Layer):} Manages storage, retrieval, and management of data, abstracting databases and external APIs from upper layers.
\end{itemize}

\section{Design Patterns}

Five core design patterns were applied across the codebase for modularity, testability and maintainability:

\begin{table}[H]
\centering
\renewcommand{\arraystretch}{1.4}
\begin{tabularx}{\textwidth}{|L{2.8cm}|L{4.2cm}|X|}
\hline
\rowcolor{isiBlue}
\textcolor{white}{\textbf{Pattern}} &

\textcolor{white}{\textbf{Purpose}} \\
\hline
\textbf{Three-Tier Architecture} &  Separates presentation, business logic and data layers so changes in one layer do not ripple through the others. \\
\hline
\textbf{Repository Pattern} &  Encapsulates all SQL queries in dedicated repository modules; controllers never write SQL directly. \\
\hline
\textbf{Service Layer} &  Centralises external integrations (Supabase, Hugging Face, Stripe) so controllers remain agnostic of provider details. \\
\hline
\textbf{Provider Pattern}& Shares state globally across React components without prop drilling; context subscribers receive updates automatically. \\
\hline
\textbf{Middleware Chain} & Composable middleware functions run before controllers; the chain stops at the first failure, enforcing authentication and authorization. \\
\hline
\end{tabularx}
\end{table}

The development relied on a carefully selected set of open-source and cloud-based tools
spanning the entire delivery chain: code editing, version control, automated integration,

  A lightweight, open-source source-code editor developed by Microsoft, available on

  An open-source containerization platform that packages an application and all its

\toolentry{logo_hostinger.png}{Hostinger}{\cite{hostinger}

\toolentry{logo_drawio.png}{draw.io}{\cite{drawio}

\toolentry{logo_eslint.png}{ESLint}{\cite{eslint}

\toolentry{logo_react.png}{React}{\cite{reactdoc}
  A declarative, component-based JavaScript library for building user interfaces,

\toolentry{logo_threejs.png}{Three.js + Model Viewer}{\cite{threejs, modelviewer}

\toolentry{logo_socketio.png}{Socket.IO}{\cite{socketio}

  It was used to implement the real-time team chat and the live notification feed

\toolentry{logo_express.png}{Express.js}{\cite{expressdoc}
  A minimal and flexible Node.js web framework chosen to expose the REST API and
  compose the security middleware chain covering authentication, authorization,
  rate limiting and input validation.}

\toolentry{logo_tailwindcss.png}{Tailwind CSS}{\cite{tailwindcss}
  A utility-first CSS framework that provides low-level design tokens directly as
  class names. It was applied consistently across both interfaces for responsive layout
  and component styling.}

\subsection{Programming Languages}

\begin{itemize}[leftmargin=2em, itemsep=4pt]
  \item \textbf{JavaScript (ES2022)} — Primary language across the entire stack:
        React component logic on the client, and Express controllers, repositories and
        services on the server~\cite{nodedoc}.
  \item \textbf{JSX} — React's syntactic extension that allows HTML-like markup to be
        written directly inside JavaScript source files to describe component trees.
  \item \textbf{HTML5 \& CSS3} — Structural and visual foundation of both single-page
        applications, largely abstracted by Tailwind utility classes.
  \item \textbf{SQL (PostgreSQL dialect)}~\cite{pgdoc} — Used for the full relational
        schema, all migration scripts and the parameterised repository queries.
  \item \textbf{Python} — Used exclusively in the offline training phase of the AI
        components: sentiment analysis and intent classification models are trained with
        scikit-learn and then served at runtime through the HuggingFace Inference
        API~\cite{huggingface}.
\end{itemize}

\subsection{Data Persistence and Cloud Services}

\toolentry{logo_postgresql.png}{PostgreSQL}{\cite{pgdoc}
  An open-source object-relational database system used as the primary data store.
  The schema spans twenty-eight tables covering users, assets, orders, RBAC, workspace
  entities and AI-generated data, with all access going through parameterised
  repository queries.}

\toolentry{logo_supabase.png}{Supabase}{\cite{supabasestorage, supabaseauth}
  An open-source Backend-as-a-Service platform built on PostgreSQL. It was used for
  cloud file storage: a public bucket for thumbnails and profile pictures, and a
  private bucket for three-dimensional asset files served through time-limited signed
  URLs.}

\toolentry{logo_stripe.png}{Stripe}{\cite{stripeapi}
  An international payment processing platform used to handle card payments through
  the Payment Intents API. It was integrated alongside a local Tunisian gateway to
  support both international and dinar-denominated transactions.}

\toolentry{logo_huggingface.png}{Hugging Face}{\cite{huggingface}
  A machine learning platform providing hosted inference APIs. It was used to run the
  DistilBERT sentiment classification model for automatic review analysis and the
  Qwen2.5-72B-Instruct large language model that powers the AI chatbot.}

\toolentry{logo_jwt.png}{JSON Web Token (JWT)}{\cite{jwt}
  An open standard for compact, self-contained tokens used to transmit authentication
  claims between the client and the server. Every protected API route verifies the
  token signature and checks the in-memory revocation list before processing a request.}

\section{Global Use Case Diagrams}

The project is composed of two applications sharing the same backend: the public
\textbf{IGS Marketplace} and the internal \textbf{IGS Workspace}. Each one has a distinct
set of actors and capabilities, so a dedicated use case diagram is presented for each.

\subsection{Marketplace --- Use Case Diagram}
The Marketplace serves external users (visitors, members, sellers) and a single internal
actor (intern) who can request supervised access to paid IGS-owned assets. The actor
hierarchy follows the role inheritance defined in the RBAC model: a \texttt{Member} extends
a \texttt{Visitor}, and a \texttt{Seller} extends a \texttt{Member}.
